# Saathi Landing Page Brief

This file is the clean knowledge handoff for building a strong Saathi landing page.

It exists because the first landing attempt was not good enough.

The goal here is not to dump code ideas.
The goal is to define:

- what Saathi actually is
- what the landing page should make a visitor feel
- what sections the page should have
- what product truths must be shown
- what visual direction to follow
- what to avoid

---

## 1. What Saathi actually is

Saathi is a Class 10 study-planning system.

It is not:

- just a timetable generator
- just a chatbot
- just a task manager
- just a calendar layer

It is a planning system that tries to do this:

```text
Student talks naturally
-> Saathi understands the goal and reality
-> Saathi locks a clean study contract
-> Saathi turns that contract into timed sessions
-> Saathi verifies the plan with code
-> Saathi shows a draft for review
-> Saathi commits the approved plan
-> Saathi tracks progress
-> Saathi repairs the future when life changes
```

That is the real product essence.

The landing page should communicate that Saathi is:

- conversational
- realistic
- progress-aware
- adaptive
- calm
- trustworthy

---

## 2. Core promise the landing page must communicate

The landing page should make the visitor understand this promise fast:

```text
Tell Saathi what you need to study and what your week looks like.
Saathi will build a realistic weekly study plan,
show it clearly,
track what really happened,
and help you adapt when the week changes.
```

That is the heart.

Not:

```text
AI! agents! orchestration! memory! vector db! supervisor!
```

Those are implementation details, not homepage value.

## 3. Product truths that are actually worth showing

These are the strongest real product features to communicate:

### A. Natural planning conversation

Student does not fill a rigid form.
They talk naturally.
Saathi converts that into a usable planning contract.

### B. Realistic weekly planning

Saathi is not supposed to make fantasy plans.
It considers:

- available time
- blockers
- effort
- progress
- constraints

### C. Draft before commit

The user can review the plan before it becomes final.

This is a major trust feature.

Show this as whole-plan approval:

```text
SkedioAI drafts several slots
-> the user reviews the proposed schedule
-> one approval commits the draft
```

Do not make it look like each slot is approved separately.
The approval belongs to the plan.

### D. Progress tracking

The user can:

- mark sessions complete
- skip them
- track what actually got done
- feed that back into future planning

Checklist ticks should mean real learner progress.
If the landing page shows checklist items inside a draft slot, show them as read-only and empty.
Do not pre-check them after plan approval.

### E. Calendar-aware planning

The system can use visible calendar blockers so plans are less stupid.

### F. Rescheduling / future repair

This is one of the most important product strengths.

If life changes, Saathi should help repair the week calmly.

The landing page can show this with a demo:

- existing blockers stay fixed
- draft study slots float into open gaps
- “Change it” shows an alternate draft
- “Approve plan” commits the whole proposed schedule
- clicking a draft slot shows its read-only checklist

Make sure draft variants do not overlap fixed blockers.

### G. Memory / personalization

Saathi should not behave like every week starts from zero.
Progress history and prior work matter.

### H. Notification / email layer

The product also has the idea of notifying or alerting when conflicts or drift happen.

This should be shown lightly.
Not overhyped.

## 4. What the landing page should NOT overfocus on

Do not overfocus on:

- internal agents
- supervisor
- intake/planner naming
- LangGraph
- Neo4j
- vector DB
- JSON contracts
- technical validation details
- tool names

Those are useful for engineering.
They are not the landing-page story.

Also do not overfocus on:

- exam panic only
- “study 14 hours a day”
- tuition / school / bedtime examples everywhere
- overly narrow “Monday exam” storytelling

Saathi is for Class 10 study planning broadly.
Not only last-minute exam rescue.

## 7. Visual direction

### Colors

Dark theme by default.

Desirable palette:

- deep charcoal / near-black background
- soft white typography
- indigo / violet accents
- occasional muted green for success / progress

### Typography

Use strong contrast:

- elegant serif for big hero lines
- clean sans-serif for product copy

The serif should make the product feel thoughtful, not academic in a stiff way.

### Motion

Use subtle motion only:

- fade in
- slight float/parallax
- soft hover response
- gentle reveal

No noisy animations.
No overdone glass gimmicks.

### Product preview style

Show believable product windows/cards:

- calendar preview
- chat preview
- draft review preview
- session/progress preview

These should feel like real UI glimpses, not random fake dashboard boxes.

## 8. Recommended page structure

This is the recommended landing flow.

### 1. Hero

Purpose:

- immediately explain what Saathi is
- give emotional hook
- show product confidence

Hero should answer:

- what is it?
- who is it for?
- why is it different?

Example direction:

```text
Study planning that actually adapts to real life.
Talk naturally, get a realistic weekly plan, track what happened, and repair the week when things change.
```

Hero needs:

- main headline
- short supporting line
- CTA
- app preview

### 2. Trust / product belief strip

Very small strip or cards showing:

- realistic plans
- progress-aware memory
- calendar-aware scheduling

This is not a logo farm unless you actually have logos worth showing.

### 3. “What Saathi does”

A feature section that explains the product loop clearly.

Best feature themes:

- conversational intake
- realistic plan generation
- progress tracking
- rescheduling / repair
- calendar awareness
- notifications/reminders

### 4. Product preview section

Show how the app actually looks and behaves:

- weekly calendar
- chat drawer
- session cards
- review state

This is where the visitor should begin imagining usage.

### 5. Workflow section

Simple 3–4 step flow:

```text
Talk
-> Plan
-> Review
-> Track and adapt
```

This should make the system feel understandable and calm.

### 6. “Why it feels better”

This section should explain the difference from ordinary planners:

- not generic
- not a form
- not fake productivity
- not rigid

Focus on:

- conversation
- realism
- adaptive weekly repair

### 7. CTA / final section

End with a clean CTA:

- Open app
- Get started
- Start planning

If separate website:

- CTA should send user to app domain

## 12. What makes Saathi genuinely different

The landing page should lean into the real differentiators:

### Not just planning — planning plus repair

A lot of products can generate a plan.
Fewer feel good when the week breaks.

### Not just a chatbot — contract-driven planning

The system is not supposed to just talk nicely.
It is supposed to stay grounded.

### Not just checkboxes — progress truth feeding future plans

The progress system is not decoration.
It is part of personalization.

### Not just calendar sync — calendar as realism support

Calendar matters because it makes plans less fake.

### Not just reminders — reminders as support when the plan drifts

Email/notifications should be framed as support, not spam.

---

## 13. What to avoid in the build

Avoid these design mistakes:

- too many sections
- too much text
- huge blocks of explanation with no product visuals
- fake empty screenshots
- generic startup gradients with no hierarchy
- too many badges/pills
- random motion everywhere
- overcomplicated nav
- too much auth UI on the landing page

If it is a separate website:

- the landing page should market
- the app should handle the real auth/product flow

So landing page should not become a login form with decorations.

---

## 14. Practical build recommendation

Best final structure:

### Separate website

- root domain / marketing site
- static or light frontend
- hero + features + product preview + CTA

### Separate app

- subdomain like `app.skedio...`
- auth
- actual product

This separation is cleaner and more serious.

Run the main app:

